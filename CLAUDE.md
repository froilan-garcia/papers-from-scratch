# papers-from-scratch — Literature reviews + paper implementations

Froilán's workspace (BSc in Physics and Mathematics, University of Oviedo; MSc in Big Data Analytics at UC3M from September 2026) for reading scientific papers, writing structured reviews and implementing their content in Python.

## Language

- **Everything committed to the repo is in English.** Reviews, `README.md`, `DERIVATIONS.md`, `ROADMAP.md`, `papers/INDEX.md`, code, comments, commit messages, figure labels and console output. The repo is public and works as a portfolio for quant applications in London and Amsterdam; a reader must not run into Spanish halfway through.
- **The conversation with Froilán is in Spanish.** This is about the language of the artefacts, not the language we work in.
- Technical terms with no settled translation stay in English anyway (*embedding*, *gauge*, *shrinkage*).

> Watch the two places that are easy to miss because they are not markdown: the
> **labels and titles of the figures** (they are embedded in the documents, so they are
> visible even when the surrounding text is already English) and the **console output**
> of the scripts, which is the first thing anyone who clones and runs will see.

## Structure

```
papers/            Original PDFs. Naming: <year>-<first-author>-<short-title>.pdf
                   The .pdf files are NOT versioned (weight + copyright: the repo is public).
                   The inventory with download links is papers/INDEX.md, which is versioned.
reviews/           One markdown review per paper, same slug as the PDF.
implementations/   One folder per paper, same slug. Each with its own README.md.
tools/             Maintenance scripts for the repo itself, not for any paper.
ROADMAP.md         Candidate papers organised by master's course; tick off completed ones.
```

## Review template (`reviews/<slug>.md`)

```markdown
# <Paper title>
**Authors:** · **Year:** · **Venue:** · **Link/DOI:**
**Field:** physics / mathematics / ML · **Read:** <date>

## TL;DR (3-5 lines)
## Context and motivation
## Methodology
   (with the key equations in LaTeX — see the note on the two forms below)
## Main results
## Strengths and limitations
## Implementation ideas
   (what is worth reproducing and at what scope)
## Connections
   (with other papers already reviewed — link their reviews)
```

## Implementation conventions

- **Python ≥ 3.11.** Base stack: `numpy`, `scipy`, `matplotlib`; `pandas`/`polars` for data; `torch` for deep learning; `sympy` for symbolic computation.
- Each implementation is self-contained in `implementations/<slug>/` with:
  - `README.md`: which part of the paper it reproduces, how to run it, and a comparison of results against the paper's.
  - `DERIVATIONS.md`: **the full mathematical development** (see below).
  - Executable `.py` scripts; notebooks only for exploration and final figures.
  - `requirements.txt` if anything outside the base stack is needed.
- Prioritise pedagogical clarity over performance: the goal is to understand the paper, not to ship production code.
- Reference in the code the equation or section of the paper being implemented (e.g. `# Eq. (12), Sec. 3.2`).
- Always validate against results from the paper (a figure, a table or a numerical value) and record the comparison in the README.
- **Publish only what is understood in depth.** Work that runs but is not yet commanded stays local (gitignored, with its notes preserved), and the README's status box says explicitly what is missing and why. A documented absence is better than an overclaimed result.

## `DERIVATIONS.md` — the mathematical development

One `.md` per implementation, with the mathematics of the topic developed **end to end**, to be read straight through as a chapter rather than consulted.

- **Logical, progressive order, not the paper's.** The document is one's own development: start from the problem, simplify it, solve it in the easy cases and generalise. Each section opens by saying what is needed next and why, and builds on what has already been derived. **It is not a formula-by-formula audit of the paper.**
- **Connect, do not enumerate.** When the same idea reappears (a non-differentiability, an eigenvector, a linearisation trick), say so explicitly: the value is in the network, not in the isolated pieces.
- The paper's numbering is cited **in passing** ("this is its Eq. 3"), at the end of the derivation and not as a headline. Never open a section by quoting what the paper claims.
- All mathematics in LaTeX, in a fenced block tagged `math` when it is a central step. No skipping "obvious" steps. See the note on the two forms below.
- Standard mathematical register in the first person plural (*"we now show that"*, *"it follows that"*, *"note that"*). The document doubles as a writing sample, so the prose matters as much as the algebra.
- **With embedded figures**, generated by a dedicated script (e.g. `derivation_figures.py`) and **computed with the solver**, not drawn by hand — so that each figure checks what it accompanies instead of illustrating it. Below each one, a paragraph saying what to look at.
- An index at the start with internal links.
- If an erratum, a missing limit of validity or an ambiguity turns up, it goes **in its place within the development**, with the numerical check that backs it — not in a separate errata section.

## LaTeX that survives GitHub

The repo is read on GitHub, and GitHub rewrites the source before any mathematics is parsed. **A backslash before an ASCII punctuation character is a Markdown escape and is deleted**, so `\,` `\;` `\#` `\{` `\}` `\|` arrive at the renderer as bare punctuation; **asterisks pair up as emphasis** and vanish, taking `X^*` with them. A backslash before a *letter* is left alone, which is why `\hat` and `\frac` always look fine and hide the problem until a document is read closely on the rendered page.

Two forms are immune, and they are the ones to use:

- **Display:** a fenced block tagged `math`, never a `$$` pair. Moving the delimiters onto their own lines does *not* help — both spellings are rewritten identically.
- **Inline:** `` $`...`$ `` whenever the expression contains a backslash before punctuation, an asterisk, or anything else that is not a letter. Plain `$...$` is fine — and more readable in the source — when every escape is before a letter, as in `$\hat\sigma^2/n$`.

This was established by feeding both spellings through `api.github.com/markdown` and reading back what survives, not by reasoning about the rules. That endpoint needs no authentication and works on a private repo, which is why `tools/check_math.py` can use it.

```bash
python tools/check_math.py             # offline, instant — run it before committing
python tools/check_math.py --github    # ask GitHub itself; the ground truth
```

Run it after writing any document with mathematics in it. The offline pass applies the rules above; the `--github` pass posts each file to that endpoint and reports anything that came back different from what went in, which is how to settle a new doubt instead of arguing with the specification.
