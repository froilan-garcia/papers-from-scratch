# Paper: review + implementation

Run the repo's full flow for a paper: get the PDF → read it → write the review →
implement what is reproducible. The formatting conventions, review template and Python
stack live in the repo's `CLAUDE.md`; this skill defines the process, not the format.

The argument can be a local path to a PDF, a URL, or a title/identifier (arXiv, DOI).
If there is no argument, ask which paper they want to review.

## Step 1 — Get the PDF

- **Local path**: if it is not already in `papers/`, copy it there, renaming to the
  convention `<year>-<first-author>-<short-title>.pdf`. That slug (without `.pdf`) is
  reused in `reviews/` and `implementations/` — decide it carefully here.
- **URL**: download it to `papers/` with the same naming scheme. For arXiv, use the URL
  `https://arxiv.org/pdf/<id>`.
- **Title or vague reference**: search the web (arXiv, Semantic Scholar, Google
  Scholar) and confirm with the user that it is the right paper before downloading, so
  as not to review the wrong article.

## Step 2 — Read and write the review

Read the whole PDF (use the PDF skill if OCR or extraction is needed). Write
`reviews/<slug>.md` **in English**, following the `CLAUDE.md` template exactly. While
writing it:

- Transcribe the key equations in LaTeX; they are the basis of the later
  implementation.
- Under "Connections", check which other reviews already exist in `reviews/` and link
  the related ones — the repo's value grows with that network of connections.
- Under "Implementation ideas", be concrete: which figure, table or numerical result of
  the paper can be reproduced, and with what data.

## Step 3 — Propose the scope of the implementation

Before writing any code, summarise for the user what you propose to implement (which
result of the paper is reproduced, what is simplified, estimated compute time) and wait
for their confirmation. Papers often require unaffordable data or compute; agreeing the
scope avoids useless implementations.

## Step 4 — The mathematical development

Before or alongside the code, write `implementations/<slug>/DERIVATIONS.md`: the
mathematics of the topic developed end to end, in **its own logical order**, to be read
straight through. The format is in `CLAUDE.md`.

The first task is to design that order, and it does not come from the paper's table of
contents. Ask what the minimum is to state the problem, what simplifies it, which
special case can be solved entirely by hand, and what has to be added to lift each
restriction. That dependency tree is the script. Papers expound in order to convince,
not to build: their order is almost never the useful one.

Derive **everything** you use, including what the paper takes for granted — which is
usually a lot: the *"are easily shown to be"*, the *"one can show"*, the formulas simply
asserted. Do not accept a step because "it is clear": if deriving it turns up an
erratum, a missing limit of validity or an ambiguity, document it in its place with the
numerical check that backs it.

Figures are generated by a dedicated script and computed with the solver already
implemented, so that each one validates what it accompanies.

## Step 5 — Implement (a bit at a time)

The user prefers to implement incrementally: first read the paper, then program in
pieces across several sessions — never all the code at once. The aim is for him to
understand each piece, so implement only the part he asks for at each moment, explain
the code and connect it with the paper's equations.

Create `implementations/<slug>/` following the `CLAUDE.md` conventions (clear scripts,
references to the paper's equations, a `README.md` with instructions and a comparison of
results). Run each part and verify that it reproduces — at least qualitatively — the
paper's result; record the comparison in the README. If the results do not match, say so
honestly in the README instead of papering over it: a documented discrepancy is a result
too.

Publish only what is understood in depth: anything that runs but is not yet commanded
stays local and gitignored, with the README saying explicitly what is missing and why.

## Step 6 — Close

Finish with a summary: where each file ended up, what was reproduced and what is
outstanding. If the repo uses git, offer to commit.
